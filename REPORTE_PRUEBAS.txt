2. QUÉ SE CONSTRUYÓ Y QUÉ SE CORRIGIÓ
============================================================================

2.1 Modo distribuido opcional
  - backend/src/config/env.ts: banderas QUEUE_MODE, NODE_ID, JOB_CONCURRENCY,
    JOB_POLL_MS, JOB_HEARTBEAT_MS, JOB_STALE_SECONDS, ANALYZER_POOL_SIZE,
    ANALYZER_TIMEOUT_MS, FAIL_ANALYZER, TRUST_PROXY. Todos con valores por
    defecto que conservan el modo simple.
  - backend/prisma/schema.postgres.prisma: esquema PostgreSQL con la tabla
    ScanJob (cola persistente), además de las tablas de la V1.
  - backend/src/modules/jobs/: repositorio con SQL crudo y
    FOR UPDATE SKIP LOCKED, reclamo atómico, latido, reasignación de trabajos
    huérfanos, límite de intentos y estado DEAD; worker de consumo con cierre
    ordenado; job-notifier.ts para despertar al consumidor local al encolar.
  - backend/src/modules/audits/audits.service.ts: encola cuando
    QUEUE_MODE=true y avisa al worker local; en modo simple ejecuta como la V1.
  - backend/src/scanners/core/: registro de analizadores, pool de hilos
    (worker_threads) con timeout, reinicio y fallback; ANALYZER_POOL_SIZE=0
    conserva la ejecución secuencial de la V1; el motor emite eventos de
    progreso y no persiste hallazgos si el objetivo falla por completo.
  - backend/src/shared/events.ts: eventos de progreso/estado.
  - X-Node-Id en las respuestas y datos de cola/nodo en /api/health.
  - TRUST_PROXY y cuotas RATE_LIMIT_MAX / RATE_LIMIT_READ_MAX elevadas para
    que el rate limit no enmascarara las pruebas.

2.2 Contenedores e infraestructura
  - backend/Dockerfile multi-stage y backend/.dockerignore.
  - docker-compose.distributed.yml: postgres, migrate, api-1 (siempre),
    api-2/api-3 (perfil scale), target-sim y nginx; healthchecks y espera a
    que migrate termine.
  - infra/nginx.3nodes.conf e infra/nginx.1node.conf: upstreams, keepalive 128,
    proxy timeouts y cabeceras.
  - tools/target-sim/server.js: objetivo simulado con endpoints de
    configuración (latency, jitter, failRate, down) y /__reset.
  - loadtest/: read.js (autocannon, medianas y desglose de errores),
    audits.js (creación y seguimiento por ID), chaos-kill-node.sh (SIGKILL),
    common.js y README.md.
  - docs/PROTOTIPO_DISTRIBUIDO.md: uso y variables.

2.3 Correcciones relevantes
  - EXAMPLE_AUDIT_ENABLED=false en el compose distribuido para no generar
    auditorías a example.com durante las pruebas.
  - El backend escanea la URL que recibe en cada auditoría; el harness pasa
    http://target-sim:8081 y el contenedor la resuelve por DNS de Docker.
  - SCAN_TIMEOUT_MS=5000 para que E6 (latencia 8000 ms) falle por timeout.
  - Si el objetivo no responde en absoluto, la auditoría queda FAILED y no se
    guardan hallazgos (evita falsos positivos); se conservan resultados crudos
    parciales y errores de analizador.
  - El cierre ordenado (SIGTERM) está implementado para liberar los trabajos;
    la prueba de caos usa SIGKILL a propósito para forzar la reasignación por
    latido vencido.
  - audits.js consulta cada auditoría por ID porque GET /api/audits devuelve
    como máximo 50 filas y E5 crea 120. Sin esta corrección el harness se
    quedaba esperando; la corrida final de E5 terminó limpia.
  - Tras recrear contenedores de API hay que reiniciar NGINX para que
    re-resuelva las IPs de los upstreams. Está documentado en los comandos.

2.4 Modo simple preservado
  - Sin QUEUE_MODE el backend usa SQLite y ejecuta la auditoría en el mismo
    proceso, como la V1.
  - npx tsc --noEmit: OK.
  - npm test: 4 suites, 33/33 tests OK.
  - No se modificó el flujo de npm run dev / npm run start ni el despliegue

7. CUELLOS DE BOTELLA Y AJUSTES APLICADOS
============================================================================

7.1 NGINX sin keepalive hacia los upstreams
  Síntoma: NGINX abría una conexión nueva al backend por cada petición; el
  costo de establecimiento y el consumo de CPU de NGINX limitaban el
  throughput.

  Ajuste aplicado: keepalive 128 en los bloques upstream de
  infra/nginx.3nodes.conf e infra/nginx.1node.conf.

  Antes (calibración 100 conexiones, 10 s, 1 repetición, sin keepalive):
    req/s = 1.199,00 · p50 = 78 ms · p97.5 = 125 ms · p99 = 165 ms
    errores = 0,00 % (0/11.990)
    NGINX CPU = 73,60 %
    Una segunda medición "antes" (el restart de NGINX había fallado, así que
    seguía sin keepalive) dio 1.452,80 req/s · p50 64 ms · p97.5 108 ms ·
    p99 118 ms · 0,00 % (0/14.528). Rango antes: 1.199–1.453 req/s.

  Después (mismo escenario, con keepalive):
    req/s = 2.036,60 · p50 = 47 ms · p97.5 = 69 ms · p99 = 82 ms
    errores = 0,00 % (0/20.365)
    NGINX CPU = 68,14 % (menos CPU que antes, con más throughput)

  Resultado: +40 % a +70 % de throughput según la referencia "antes", y
  p50 ~40 % y p99 ~50 % menores. Se mantiene el ajuste.
  Limitación: es una calibración de 10 s y 1 repetición; la primera medición
  "antes" tuvo target-sim al 21,65 % (posible auditoría residual) y la de
  "después" al 0 %. Para un número definitivo habría que repetir con más
  repeticiones y el sistema en reposo.

7.2 Latencia de sondeo de la cola (1000 ms)
  Síntoma: una auditoría encolada podía esperar hasta 1 s antes de que un
  worker la reclamara; con 30 auditorías y concurrencia de workers 12
  (4 por nodo) se veían varias "olas" de espera y el tiempo medio se inflaba.

  Ajuste aplicado: aviso local inmediato al encolar (job-notifier.ts) +
  JOB_POLL_MS=250 como respaldo para trabajos encolados por otras réplicas.

  Antes (3 nodos, pool 3, JOB_POLL_MS=1000, 30 auditorías, concurrencia 10):
    total = 3,13 s · 575,45 auditorías/min · media = 1,80 s
  Después (3 nodos, pool 3, aviso + 250 ms, 30 auditorías, concurrencia 10):
    total = 1,31 s · 1.371,95 auditorías/min · media = 0,39 s
  Corrida posterior con el mismo ajuste:
    total = 1,20 s · 1.502,50 auditorías/min · media = 0,18 s
  Comparación secuencial pool 3 (misma sesión de pruebas): media = 0,25 s.

  Resultado: el tiempo medio baja de 1,80 s a 0,39 s (–78 %) y las
  auditorías/min suben de 575 a 1.372 (+138 %) en la comparación directa.
  Se mantiene el ajuste.

7.3 Cuello de botella observado sin ajuste: CPU/PostgreSQL
  A 50 conexiones (E3) el clúster da 854,94 req/s; a 100 conexiones (E4) da
  849,00 req/s: no hay ganancia de throughput y la latencia se duplica
  (p50 55→112 ms, p99 101→192 ms). Los tres backends consumen ~200 % cada uno
  (≈6 hilos lógicos), Postgres ~120–129 % y NGINX ~43 %. La carga agregada
  roza la saturación de los 6 núcleos físicos del host.

  Ajuste propuesto (NO aplicado, fuera del alcance del prototipo):
    - Más réplicas o más CPU física para repartir la carga.
    - Índice compuesto en Audit(userId, startedAt) para el listado.
    - Caché de la lista de auditorías o paginación explícita.
  No se aplicó porque requiere cambiar la infraestructura o el alcance y no
  era necesario para validar la arquitectura distribuida.

7.4 Primera pasada de E3/E4 vs pasada final
  La primera pasada de E3/E4 dio 1.137,97 y 1.152,07 req/s. La pasada final,
  con el mismo binario y la misma configuración, dio 854,94 y 849,00 req/s.
  La comparación secuencial pool 0 vs pool 3 (845,10 vs 854,94 en E3; 867,04 vs
  849,00 en E4) confirma que la diferencia no es del pool. Se atribuye a
  varianza térmica/orden y al estado del host tras varias pruebas sostenidas.
  En la tabla de la sección 3 se usa la pasada final consistente; la primera
  se conserva como evidencia de la variabilidad.

============================================================================
8. LIMITACIONES PENDIENTES
============================================================================

1. Varianza térmica/orden: el host es de escritorio y Docker Desktop comparte
   CPU con el generador de carga. La primera pasada de E3/E4 fue ~25–35 % más
   rápida que la final; se reporta la final y se documenta la primera. No es
   un benchmark certificado.
2. docker stats es una muestra puntual a mitad de cada escenario, no un
   perfil continuo; los picos de CPU/memoria pueden ser mayores.
3. Docker Desktop limita la memoria visible a 13,6 GiB, aunque el host tiene
   27,9 GiB. Las cifras de memoria son relativas a ese límite.
4. El generador de carga (autocannon) corre en el mismo host y compite por
   CPU con los contenedores.
5. La prueba de lectura solo ejerce GET /api/audits; no mide escrituras,
   mezcla de lectura/escritura ni el frontend.
6. No hay terminación TLS/HTTPS en NGINX para estas pruebas: el tráfico es
   HTTP en localhost:8080 y el objetivo simulado es HTTP. No se midió
   handshake TLS real.
7. No se probó failover de PostgreSQL ni particiones de red; E5 solo mata un
   nodo de API con SIGKILL. La base de datos es un único contenedor.
8. No se hizo una prueba de soak larga: las pruebas de lectura son 30 s × 3
   por escenario y E5 dura ~43 s. No se observó degradación en ese tiempo,
   pero no se puede afirmar comportamiento en horas.
9. El pool usa worker_threads, no procesos separados. Analizadores pesados
   seguirían compitiendo por la CPU del mismo contenedor; la mejora del pool
   es modesta con los analizadores actuales.
10. La cola tiene estado DEAD y límite de intentos, pero no hay alertas ni
    métricas exportadas más allá de /api/health. No se probó el camino DEAD.
11. target-sim es un mock controlado; sitios reales tienen TLS, redirecciones,
    WAF, CDN y latencias variables. Los resultados no se extrapolan
    directamente a producción.
12. Las pruebas de 1 nodo usan el mismo host y la misma VM de Docker, no una
    máquina separada.
13. EXAMPLE_AUDIT_ENABLED=false en el compose distribuido para no escanear
    example.com. En modo simple el valor por defecto sigue siendo true.
14. El harness audits.js se corrigió para consultar por ID porque el listado
    devuelve máximo 50 filas; la primera corrida de E5 se quedó esperando por
    esa causa. La corrida final de E5 es la válida y terminó limpia.
15. Los números provienen de una sola máquina y de una corrida por escenario
    (3 repeticiones en lectura). No constituyen una certificación de
    rendimiento.
